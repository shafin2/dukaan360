# Client-Reported Requirements (v1 QA Feedback)

Source: `Dukaan360_Updates_Requirements.docx`, a functional-requirements/QA doc shared by the client running v1 in production (screenshots show the real tenant — "Eman Traders" business, "Bao Mushtaq Sweets" / "Eman Branch Gulberg" shops, confirming the sweets/mithai vertical noted in [01-vision-and-problem.md](./01-vision-and-problem.md)). These are 11 concrete, specific bugs and gaps a real user hit using the live app — the most direct, ground-truth input into this rewrite of everything in this docs folder. Unlike the competitor/market research, these aren't inferred priorities — they're reported pain.

Each item below carries the original requirement plus what it means for the rewrite. Several are not just bug fixes — they're data-model or auth-architecture decisions that need to be made correctly in Phase 1 of [09-roadmap.md](./09-roadmap.md), not patched later.

## 01. Discount on Udhaar/Credit sales
**Requirement:** Discounts must apply to credit (Udhaar) transactions the same way they apply to other bill types. The discounted amount must be reflected correctly in the bill, the outstanding balance, and reports.
**Rewrite implication:** v1's `Bill` schema already has `discountType`/`discountValue`/`discountAmount` fields independent of `billType` — so this is very likely a UI-layer or validation-layer bug (discount control disabled/hidden for `billType: credit`) rather than a missing schema field. Confirm in the new backend that discount calculation, outstanding-balance calculation, and report aggregation all read from the same discount fields regardless of bill type, and write a test case specifically for "credit bill with a discount" — this exact combination is what broke.

## 02. Worker: restrict to today's data only
**Requirement:** Worker accounts should only be able to filter by "Today" — not switch to monthly/weekly/yearly/custom ranges — unless the business owner explicitly grants it. Privacy/scope reason, not just UX.
**Rewrite implication:** This is a role-based access control rule, not a UI hint — enforce it server-side (the date-range parameter on report/sales endpoints must be validated against the caller's role, not just hidden in the frontend dropdown). Ties directly into the profit-visibility gating already identified as a differentiator in [02-current-state-audit.md](./02-current-state-audit.md) — this is the same category of control (limit what a Worker can see) and should be designed as one coherent permission system, not two separate hacks. Add "explicitly permitted by owner" as a per-worker override flag, not a global toggle.

## 03. Item count when adding items
**Requirement:** Show a live, updating count of items whenever items are added to a bill or inventory action (spot items, stock distribution, etc.) — count updates immediately as items are added, removed, or quantities changed.
**Rewrite implication:** Pure frontend state/UX fix — straightforward once the form state is properly reactive. No backend implication. Low complexity, worth doing early since it's cheap and visibly polishes a screen every Worker touches daily (bill creation).

## 04. Sortable columns & table filters
**Requirement:** Add sorting to relevant table columns and filters where needed, without users losing their current table context (filter/sort state) while working.
**Rewrite implication:** This is a real API-shape decision, not just frontend: list endpoints (sales, bills, inventory, customers) need to accept `sort`/`filter` query params server-side rather than sorting/filtering client-side over a full fetched page — otherwise it won't scale past a small dataset and won't compose with pagination. Design this once as a shared list-query convention across all table endpoints in the new API, rather than bespoke per screen.

## 05. Historical sale price logic
**Requirement:** When an item's selling price is reduced, existing sales must retain the price actually used at the time of sale. Future sales use the new price. Historical profit and sales records must not be recalculated incorrectly because of a later price change.
**Rewrite implication:** v1's `Sale` model already stores `unitPrice`, `costPriceSnapshot`, `costTotalSnapshot`, and `profitSnapshot` per line item specifically to survive later price changes — so either this snapshot isn't being read consistently everywhere (some view/report is re-joining to the live `Product.sellPrice` instead of the stored `unitPrice`), or a specific code path skips writing the snapshot. **This is exactly the class of bug the Postgres rewrite should make structurally harder** — see [05-architecture.md](./05-architecture.md): make the sale/bill line-item price fields non-nullable and written once at insert time, never recomputed by joining to the current product row, and add an integration test that changes a product's price after a sale exists and asserts the historical sale's price/profit is unchanged.

## 06. Spot sale profit
**Requirement:** Show the profit generated from a Spot Sale (an ad-hoc item not in the product catalog) after deducting the item's purchasing cost. Profit must be calculated from the actual sale price and the applicable purchase cost, and shown clearly in the sale summary.
**Rewrite implication:** v1's `BillItemSchema`/spot-sale path defaults `buyPrice` to `0` for spot items — meaning profit for spot sales is currently either wrong (always shows full sale price as profit) or not computed at all. The rewrite needs to require a purchase/buy cost input at the point of spot sale entry (not silently default to 0), and compute profit the same way as catalog-item sales. This is a real gap, not just a display bug — decide explicitly whether spot-sale profit is required at entry time or estimated some other way, and don't let `0` be a silent default that quietly zeroes out profit reporting.

## 07. Reset password not working
**Requirement:** Fix the reset-password flow end to end — from requesting a reset through receiving it and successfully setting a new password. Handle invalid, expired, or already-used reset requests appropriately.
**Rewrite implication:** The screenshot shows the underlying cause: the user-edit form has an **email field that's greyed out/disabled with "Email cannot be changed"**, and a "reset password" field lives inside that same admin edit form rather than a proper self-service reset flow — for at least some accounts, email may be missing or unset, which breaks any email-based reset. This is a **P0 correctness requirement for the new auth system** (see [04-tech-stack.md](./04-tech-stack.md)'s JWT/refresh-token design): the rewrite must decide explicitly whether email is mandatory at account creation (and backfill/require it for existing accounts) or support a phone/WhatsApp-based reset path instead — given the market context, a WhatsApp-based reset (the number is already central to the product) may be more reliable than email for this user base. Whichever path is chosen, build and test the full request → token → expiry/reuse-rejection → set-new-password loop as a first-class flow in Phase 1, not an afterthought.

## 08. Item edit history / audit logs
**Requirement:** Add an audit log for item (product) edits — identify what changed, the previous value, the new value, who made the change, and when, wherever applicable.
**Rewrite implication:** v1's `AuditLog` already exists and is genuinely rigorous for some flows (stock additions log readable messages like "Added 8 units of warehouse stock for 'Kunafa cake 6pc' (buy price set to Rs 750)") — but this feedback confirms **coverage is inconsistent**, specifically for direct product field edits (name, price, category changes). The rewrite should treat "every mutation on every tenant-owned entity gets a structured, field-level audit entry" as a cross-cutting concern implemented once (e.g. a Prisma middleware or repository-layer wrapper that diffs old/new values automatically) rather than something each feature remembers to call manually — that's almost certainly why product edits fell through the cracks in v1. This reinforces the audit-trail-as-differentiator positioning in [02-current-state-audit.md](./02-current-state-audit.md); the rewrite needs to actually close this specific gap for the positioning to be true everywhere, not just in the flows that happened to call it.

## 09. Quick Sale: single transaction record
**Requirement:** A Quick Sale with multiple items should be stored and displayed as **one transaction record** containing all its items — not a separate transaction record per item. The single record must still preserve item-level detail, quantities, prices, and totals.
**Rewrite implication:** This is the most structurally significant item in this list. v1's `Sale` model is line-item level by design — a `Bill` groups multiple `Sale` line items via `billId`, but a **Quick Sale currently has no equivalent grouping container**, so buying 3 unrelated items in one quick-sale action creates 3 independent `Sale` documents with 3 separate IDs, timestamps, and rows in every list view (confirmed by the screenshot: "Krispy wafer," "Panda Jelly," "Cemak wafer" etc. each appear as their own record). **Decision for the new Postgres schema:** give Quick Sale the same shape as a Bill — a lightweight parent record (could reuse `Bill` with a `billType: 'quick'`/`cash` variant, or a dedicated `QuickSale` header table) that owns one-to-many line items, exactly like Bill already does. This isn't optional polish — it's a genuine data-model gap in v1 that the rewrite's schema design (Phase 1, [09-roadmap.md](./09-roadmap.md)) needs to resolve before any migration script runs, since migrating existing per-item Quick Sale records into grouped transactions is a real data-migration decision, not just a new-feature build.

## 10. Daily purchasing cost
**Requirement:** Show the total cost of items added to inventory (purchased) within a selected day, calculated from actual purchasing cost.
**Rewrite implication:** A new KPI/report, not a bug fix — add alongside the existing Business & Inventory KPI cards (Customers, Products, Shops, Total Inventory, Current Stock). Straightforward once the schema tracks buy-cost per stock-addition event (it already does, via `Product.buyPrice` and warehouse-distribution logging) — this is mostly a new aggregation query and a new dashboard card, worth bundling into the Phase 1 reporting rebuild rather than treating as its own project.

## 11. Show all total expenses (not just current page)
**Requirement:** The Expenses page currently shows the total for only the visible page of results; moving to the next page changes the displayed total. The total should reflect the full filtered result set, not just what's currently rendered.
**Rewrite implication:** A straightforward but important correctness bug — the total must come from a server-side aggregate query over the full filtered set (respecting the same category/shop/date filters as the list), computed independently of pagination, never by summing the client-visible rows. This is the same category of bug as the "sortable columns & filters" item (#4) above — both point to list/aggregate endpoints needing a consistent, deliberate query pattern (filter → aggregate total server-side, filter → paginate rows server-side, as two separate concerns) rather than ad hoc per-screen logic. Worth fixing once as a shared convention across every table+total screen (Expenses, Sales, Bills, Payments), not just Expenses specifically.

## Cross-cutting pattern across all 11 items

Read together, these aren't 11 unrelated bugs — they cluster into a small number of systemic gaps in v1 that the rewrite should fix structurally, once, rather than screen-by-screen:

1. **List/aggregate endpoints need a consistent server-side convention** — sort, filter, paginate, and total are currently inconsistent per screen (#4, #11).
2. **Snapshot-vs-live-value discipline isn't applied everywhere it should be** — historical price/profit correctness (#5) and spot-sale cost capture (#6) are both instances of "a value that must be fixed at transaction time is instead being read live or defaulted to zero."
3. **Audit logging is a manually-remembered call, not a structural guarantee** — hence uneven coverage (#8).
4. **Role-based scoping needs to be enforced server-side as one coherent permission system**, not per-feature UI hiding (#2, and the existing profit-visibility gating).
5. **Quick Sale's data model has a real structural gap** relative to Bill (#9) — this is the one item that needs a schema decision before migration, not just a bug fix after.
6. **Auth flows (reset password, #7) need to be built and tested as first-class flows** in the new JWT-based auth system, not retrofitted.

These six patterns should be treated as explicit acceptance criteria for Phase 1 of the rewrite, not just a backlog of 11 tickets — see [09-roadmap.md](./09-roadmap.md).

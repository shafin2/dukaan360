# Tech Stack

The original assumption going in was Next.js + NestJS + Postgres + BullMQ + Redis. Research confirms most of that — but makes one deliberate deviation (Fastify over NestJS) worth reading in full before locking it in, since it's a real trade-off, not a foregone conclusion.

## Recommended stack

| Layer | Technology | Why |
|---|---|---|
| Frontend/BFF | **Next.js (App Router)** | Kept — it's already working well for this team and there's no reason to move off it. |
| Backend API | **Fastify** (modular TS: routes/services/repos folders, Zod validation) — NestJS is a defensible fallback | For a 2–3 person team, NestJS's DI/module ceremony pays off past roughly 8–10 engineers, not before. Fastify gives 3–4x Express throughput via schema-based serialization, and built-in JSON-schema validation covers most of what Nest's guards/pipes would buy. If the team culturally wants Nest's structure anyway, run it on the Fastify adapter (not Express) with flat, one-per-domain modules (tenants, shops, billing, inventory) — that's the acceptable middle ground. |
| ORM | **Prisma ORM v7+** | Prisma 7 dropped its Rust query engine entirely — pure TS client, ~90% smaller bundle, much faster cold start — closing most of the historical gap with Drizzle. Drizzle still wins on raw query overhead and edge/serverless bundle size, but this runs as a persistent Node process on EC2, so that edge is irrelevant here. Prisma wins on migration tooling maturity and ecosystem depth, which matters more for a small team, especially one leaning on AI-assisted coding where Prisma's schema-first workflow is well understood by tooling. |
| Multi-tenancy pattern | **Shared schema, `tenant_id` (business_id) column on every table, enforced by Postgres Row-Level Security** | Schema-per-tenant or DB-per-tenant creates real operational pain past a few dozen tenants (N migrations, catalog/connection bloat) — overkill for the 50–200 shop range this needs to scale to. RLS gives a database-level backstop against the classic "forgot a WHERE clause" leak: set `app.current_tenant_id` via `SET LOCAL` in a Prisma middleware per request, and Postgres enforces isolation even if application code has a bug. This is the single biggest structural fix over v1's MongoDB approach, where tenant scoping was 100% an application-code discipline problem. |
| Background jobs/queue | **BullMQ + Redis** | Redis is already wanted for caching, so BullMQ is zero marginal infrastructure cost, and it's more feature-complete (rate limiting, delayed/scheduled jobs, priorities, retries) than Postgres-native alternatives (pg-boss, Graphile Worker), which cap around 100–200 jobs/sec before lock contention. The actual job mix here — WhatsApp send/receive, scheduled reports, low-stock alerts, nightly backups, AI calls — is low-throughput, so BullMQ's extra capability is insurance, not waste. |
| Auth | **Self-rolled JWT + Passport in the backend**, Postgres as source of truth | Lucia was deprecated (March 2025). NextAuth/Auth.js is now discouraged for anything beyond a single Next.js app and has no real multi-tenant model. Better Auth has org/RBAC plugins but is ESM-only (friction against a CJS-leaning Node backend) and assumes one app owns the session surface — awkward once the WhatsApp bot service needs to validate identity independently. Short-lived JWT access tokens + hashed refresh tokens in Postgres, with tenant/shop/role claims embedded in the JWT, let any service (Next.js, the API, the WhatsApp bot) verify statelessly against a shared signing secret. |
| Realtime | **Server-Sent Events (SSE)**, not WebSockets or polling | The actual need is one-way — push stock/sale updates to other devices at the same shop — not bidirectional. SSE runs over plain HTTP through the existing reverse proxy with zero extra infrastructure; a stateful WebSocket gateway buys nothing here. Revisit WebSockets only if a genuinely bidirectional feature (live chat) shows up later. |
| Type safety (FE↔BE) | **REST + OpenAPI + generated TS client** (Fastify-swagger/`@nestjs/swagger` → `orval`/`openapi-typescript`), not tRPC | tRPC needs both ends compiled in one TS boundary; retrofitting it onto a separately-deployed backend needs fragile generator shims. This API also needs to be reachable by a likely non-TypeScript WhatsApp bot service eventually — REST/OpenAPI is the durable, language-agnostic contract; tRPC only speaks to TS clients. |
| File/image storage | **AWS S3** (not Cloudinary, not self-hosted MinIO) | Cloudinary's free tier is tight and paid tiers get expensive fast for a low-ARPU Pakistani SaaS. Self-hosted MinIO saves the per-GB fee but competes for RAM/CPU/disk I/O on the same box already running Postgres, Redis, two Node apps, and background workers — not worth the contention at 50–200 tenants. S3 (or a cheaper S3-compatible option like Backblaze B2/Cloudflare R2 if egress cost becomes a concern) is cheap at this scale, offloads storage I/O entirely off the EC2 box, and is a five-minute SDK integration. |
| Testing | **Vitest** for Next.js + shared packages, **Playwright** for a handful of critical E2E flows (create sale, close bill, low-stock alert) | Vitest is materially faster and the current default for new TS projects. Don't over-invest in E2E coverage for a small team — a handful of critical-path flows is enough. |
| Monorepo tooling | **pnpm workspaces + Turborepo** | For a 2–3 person team splitting Next.js app + API + shared types, Nx's extra config/graph tooling is more machinery than needed. pnpm workspaces gives shared-package linking; Turborepo gives cached, parallelized builds/tests — enough structure without Nx's learning curve. |

## Explicit trade-offs and risks

1. **Dropping NestJS for Fastify loses built-in RBAC scaffolding.** Mitigate with a thin shared `requireRole()`/`requireShopAccess()` middleware and per-route Zod schemas instead of reinventing Nest's guard system.
2. **Self-rolled JWT auth is more upfront work than Better Auth/Clerk.** Justified specifically because a second service (the WhatsApp bot) needs to verify identity independently. If that requirement ever drops, Better Auth is worth reconsidering to cut boilerplate.
3. **Row-Level Security makes every query path load-bearing for tenant isolation.** A missed `SET LOCAL` on one connection-pool code path could silently leak data across tenants. Write a hard integration test asserting cross-tenant reads fail, before shipping anything to a second real tenant.
4. **Everything on one EC2 box is a single point of failure.** Postgres, Redis, and both Node apps sharing one instance means a resource spike in one (e.g. a heavy report-generation job) can starve the others. Mitigate with BullMQ concurrency limits/backoff and conservative Postgres `work_mem`/connection pool caps sized for an 8GB box.

## On NestJS vs Fastify specifically

This is the one place the original assumption changes, and it's worth the team explicitly deciding rather than defaulting. Fastify is the research recommendation given a small team; NestJS remains a completely reasonable choice if the team prefers its opinionated structure, is already comfortable with it, or expects to grow past ~8–10 backend engineers reasonably soon — in which case, run it on the Fastify adapter rather than Express, and keep modules flat and domain-scoped rather than over-nesting. Either choice is compatible with everything else in this stack (Prisma, BullMQ, RLS, JWT auth, SSE, OpenAPI).
